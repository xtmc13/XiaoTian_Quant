# XiaoTian_Quant 三栈架构缺口审计

- 审计日期：2026-11-24
- 审计范围：`gateway/`（Go）、`engine/`（Rust）、`web/`（TypeScript），构建脚本、测试、现有设计文档
- 对标对象：QuantDinger、freqtrade、币富量化 CRA（两份 PDF）、CryptoRobotics
- 目标形态：**Go（网关/账户）+ Rust（撮合）+ TypeScript（前端）**

---

## 一、先给结论

1. **三栈比例严重失衡。** Go 151,292 行、TS 87,467 行、Rust 4,477 行，约 **33 : 19 : 1**。Rust 目前是一个挂在 Go 进程里的 cdylib，不是独立的撮合层。
2. **同一笔成交有四套判定。** Rust 订单簿、Go 撮合回退、`paper_matcher` 轮询、回测 `fillPending` 各算各的；同一策略在回测、模拟盘、实盘会得到三套不同结果。
3. **账户层存在“假动作”。** `POST /account/transfer`、`/account/buy`、`/contract/leverage` 返回 `success: true`，但**不触达交易所**，只改内存或直接吞掉参数；其中划转在合约经典页有真实入口。
4. **行情与止损时效不够。** 策略 K 线靠 REST **20 秒**轮询，信号机器人 TP/SL 靠 **5 秒**轮询；1 分钟级 CRA 策略实际会滞后。
5. **CRA 功能面已补齐约九成。** 策略参数、补仓阶梯、止盈方式、移动止盈、反向止盈/止损、防瀑布、手动动作、在线单量都在；真正缺的是**点卡/激活码/团队佣金/用户收益榜/帮助中心**，以及**全所盈利保护**和**杠杆落地**。
6. **freqtrade 的研究能力基本对齐**（回测偏差、walk-forward、OOS、TPE/CMA-ES/DE、protections、pairlist、FreqAI 都有）。差的是 QuantDinger 那类**分布式运行时、审计、进程沙箱**，以及 CryptoRobotics 那类**多所实盘认证与移动端体验**。

| Go 业务代码 | 151,292 行，75 个 internal 包 |
| TypeScript 前端 | 87,467 行，39 个顶层页面 + 子目录页面 |

> 结论的基调：这不是“功能没做”，而是“功能都在，但层的边界和事实源没有收口”。

## 三、架构落位诊断

| 能力 | 当前落点 | 目标落点 | 判定 |
|---|---|---|---|
| 用户/鉴权/凭证 | Go `internal/auth`、`credential_vault` | Go | ✅ 合理 |
| 账户/余额/划转 | Go `portfolio`（内存账本） | Go | ⚠️ 有实现但是模拟 |
| 下单/OMS/风控 | Go `order`、`risk`、`app` | Go | ✅ 合理 |
| 策略运行时 | Go `strategy`（同进程 goroutine） | 独立 worker（Go 可） | ⚠️ 与网关同进程 |
| 回测/超参/因子 | Go `backtest`、`hyperopt`、`experiment` | 独立 worker | ⚠️ 与网关同进程 |
| 撮合（模拟盘） | Rust 订单簿 + Go 回退 | Rust | ⚠️ Rust 只在模拟盘局部 |
| 撮合（回测） | Go `backtest.runner` K 线撮合 | Rust | ❌ 完全未走 Rust |
| 持仓/TP-SL | Go 5 秒轮询 + Rust executor 死代码 | Rust 执行内核 | ❌ 分裂且重复 |
| 行情数据面 | Go 混合：WS tick + REST K 线 20s | Go 网关数据面 | ⚠️ 两条链路不同步 |
| 前端 | TS React | TS | ✅ 合理 |
| 服务边界 | 单 Go 二进制 + 一个 cdylib | 网关 / worker / matcher 分进程 | ❌ 未分层 |

一句话：**现在是“一个 Go 单体 + 一个 Rust 库 + 一个 React 前端”，不是“三层服务”。**

## 四、Rust 撮合层缺口

### R-01 撮合不是唯一仿真事实源（P0）

现状：

- `gateway/internal/service/matching.go:19-21` 明确写着：“生产路径当前使用 Go 撮合引擎，Rust CGo 需 `cgo && xtengine` 才启用。”
- 官方 `build.sh:70` 与 `Dockerfile:96` 又默认带 `xtengine` 构建。**代码注释与构建事实相反**，说明两套实现长期并存且没人收口。
- 模拟盘另有一套 `handler/paper_matcher.go`：每 2 秒查一次价格，价格穿过限价就**整单按限价成交**，完全不看盘口深度。
- 回测 `backtest/runner.go:348-352` 用“上一根信号、下一根开盘价成交”，与上面两套都不同。

影响：

- 同一策略在回测、Paper、实盘的结果不可比，参数优化结论无法迁移。
- Paper 成交偏乐观（无深度、假流动性），用户实盘会显著低于模拟收益。
- 无法回答“这套参数在真实盘口下会怎样”这个核心问题。

补法：

1. 定义唯一的 **Execution Core**（Rust）：`CreateOrder / CancelOrder / AmendOrder / OnMarketData / Snapshot / Replay`。
2. 回测改为“Rust 内核 + 历史 L1/L2 回放”，删除 Go 的 K 线内撮合。
3. Paper 改为“Rust 内核 + 实时行情驱动”，删除 `paper_matcher` 的 2 秒轮询。
4. Go 只负责把订单发给内核、把回报落库，不再自己做成交判定。

验收：同一策略、同一段行情、同一参数，回测 / Paper / 影子实盘三者的成交价、成交量差异可解释（滑点模型独立配置），且三条路径共用一套成交代码。

---

### R-02 撮合引擎只有 Limit / Market（P0）

现状：`engine/src/orderbook.rs:11-17` 的 `OrderType` 只有 `Limit`、`Market`。

缺：

- 条件单 / 止损单（Stop-Market、Stop-Limit）
- IOC / FOK / Post-Only / Reduce-Only
- OCO / bracket（入场 + 止盈 + 止损三腿联动）
- iceberg / TWAP 子单
- 价格带、最小名义、tick size、step size 校验
- 自成交 prevention（同一 user 买卖互撞）
- 合约语义：仓位、保证金、杠杆、强平价、资金费率

影响：CRA 的“止损单”、CryptoRobotics 的“OCO / trailing / break-even”无法在模拟内核里复现；合约策略只能靠 Go 侧另写逻辑。

补法：把订单类型扩到条件单族 + 执行约束（TIF、post-only、reduce-only），并把“仓位/保证金/强平”作为内核的一等公民，而不是 Go 策略里的浮点公式。

验收：用交易所真实订单类型做参数化回放，20 种订单组合成交结果与交易所历史逐笔对齐。

---

### R-03 状态全内存，重启即失忆（P0）

现状：`engine/src/ffi.rs` 用全局 `Mutex<HashMap<symbol, Engine>>`；`matching.rs` 的活动单、成交、盘口全在内存；没有 WAL、没有快照、没有事件序号。

影响：

- 进程重启后，Paper 的挂单、盘口、成交量全部归零；Go 侧订单表仍是 `NEW`，两边状态不一致。
- 无法做确定性回放，线上问题不可复现。
- 订单 ID 重启后重置，可能与历史成交 ID 冲突。

补法：Rust 内核加 append-only event log（每笔下单/撤单/成交/资金变动一条），定期 snapshot；启动时 snapshot + 回放；订单 ID 用持久化单调序列。

验收：kill -9 后重启，订单簿、活动单、成交序列与重启前逐字段一致。

---

### R-04 市价单状态判定有明确 Bug（P0，可当天修）

现状：`engine/src/matching.rs:100-107`

```rust
let status = if is_market || filled >= quantity {
    OrderStatus::Filled
} else if filled > 0.0 { ... }
```

只要 `order_type == Market`，无论成交多少都返回 `Filled`。空盘口下市价单实际 0 成交，仍会回报 `Filled`（内部虽然把它标成 `Cancelled`，但返回结构用的是重新计算的 `status`）。

影响：Paper 的市价单可能“0 成交但显示已成交”，仓位与余额对不上；这比缺功能更危险。

补法：删除 `is_market ||`，改为 `filled >= quantity` 才算 Filled，部分成交 `PartiallyFilled`，0 成交 `Cancelled`；补一条空盘口市价单回归测试。

验收：空簿市价单返回 `Cancelled, filled=0`；半簿返回 `PartiallyFilled`。

### R-05 单进程 FFI + 粗锁（P1）

现状：

- CGo 每笔订单一次 JSON 序列化 / 反序列化（`cgo_bridge.go`）。
- 全局 `enginesMu` + 每 symbol 一把 `Mutex`，所有订单串行。
- Rust panic 会直接拖垮 Go 进程，无法隔离。

影响：单机吞吐上限低；一个 symbol 的热点会阻塞同进程其他工作；无法灰度、无法独立扩容。

补法（二选一）：

- 短期：保留 CGo，但改批量接口（一次提交 N 笔）、二进制编码、每 symbol 独立线程 + 无锁队列。
- 中期：独立 `matcherd` 进程，gRPC/Unix socket，Go 只做客户端；崩溃可重启、可多实例按 symbol 分片。

验收：单 symbol 持续 10 万笔/秒提交，P99 < 1ms；单独压测 matcher 不影响网关 API。

---

### R-06 Rust `SignalExecutor` 是死代码（P0/P1）

现状：

- `engine/src/executor/` 已实现 Signal、PositionManager、TPSLManager、执行引擎（约 2,000 行）。
- FFI 已导出 `engine_execute_signal`、价格更新回调。
- **Go 侧没有任何调用**：`cgo_bridge.go` 只声明了 create/destroy/submit/cancel/snapshot/trades 七个函数；TP/SL 实际在 `handler/executor_tpsl.go` 用 Go 重写。

影响：

- 违背 `THREE_BOTS_DESIGN.md` 的明确决策：“TP/SL 实现层 = Rust SignalExecutor，理由是低延迟、无 GC 暂停”。
- 两份 TP/SL 逻辑（Rust 与 Go）会持续漂移，测试只覆盖其中一份。
- 4,477 行 Rust 里近一半是永不执行的代码，维护成本纯负。

补法：二选一，不要保留中间态。

- A（推荐）：接线 Rust executor，Go 只做信号入口与回报落库；删除 Go 版 TP/SL。
- B：明确放弃，删除 Rust executor 与相关 FFI，把 Rust 定位收窄为“纯订单簿”。

验收：TP/SL 只有一处实现；信号机器人在 100ms 级价格跳动下触发不晚于 1 个 tick。

---

### R-07 行情驱动是轮询 + 假流动性（P0）

现状：

- `service/matching.go:224` 的 `SimulateTrading` 每 3 秒在中间价上下挂 4 张模拟做市单，为 Paper 提供“无限流动性”。
- `handler/paper_matcher.go` 每 2 秒轮询一次交易所 REST 价格。
- `market/kline_feeder.go:26` 策略 K 线 **20 秒**轮询一次。
- `handler/executor_tpsl.go:355` TP/SL **5 秒** ticker。

影响：

- Paper 成交过于容易，回测/模拟/实盘三套结果进一步分化。
- CRA 的 1 分钟 EMA4、MACD 金叉信号最多晚 20 秒，滑点与错过入场都不可控。
- 多 symbol 时 REST 请求量 = 符号数 × 每 20 秒，容易触发交易所限频。

补法：建立单一行情总线：交易所 WS（逐笔 + 深度 + 收盘 K 线）→ 事件总线 → 策略 / Paper 内核 / TP-SL / 前端推送。删除 REST 轮询与模拟做市单（或做成显式“演示模式”开关）。

验收：收盘 K 线在交易所 close 后 ≤500ms 到达策略；TP/SL 由 tick 驱动而非 5 秒定时器；Paper 盘口来自真实深度。

---

### R-08 精度、自成交、价格带（P1）

现状：价格/数量全部 `f64`；没有 tick/step 校验；没有自成交 prevention；没有价格带/熔断。

影响：0.1+0.2 类误差在补仓阶梯、均价、止盈比例上累积；同一账户双边挂单会自成交，虚增成交量。

补法：`rust_decimal` 定点数；引入 `SymbolSpec`（tick/step/minNotional）；自成交检查；价格带拒绝。

验收：1e-8 精度下 10 万次补仓计算无漂移；同用户买卖互撞返回 `Rejected(SelfTrade)`。

---

### R-09 无 L2 增量行情（P2）

现状：只有 `snapshot(depth)`，没有增量深度订阅/维护。

影响：无法做盘口敏感策略、滑点估算、真实成交概率模型。

补法：内核维护 L2 簿，支持 snapshot + delta 序列；回测可重放。

---

### R-10 性能门禁与模糊测试（P2）

现状：有 criterion bench（`engine/benches/matching_benchmark.rs`）与内置吞吐断言，但 CI 没有性能阈值，也没有 fuzz/property test。

补法：CI 增加“单 symbol 10 万笔撮合 < X ms、内存 < Y MB”门禁；对订单状态机做 proptest。

## 五、Go 网关 / 账户层缺口

### G-01 账户动作是“假动作”（P0，最高优先级）

现状：

- `handler/account.go:52-53`：划转注释直接写着 “Simulate transfer by updating balances… In production, this would call the exchange API”，随后只手改 `binance_spot/futures/funding` 三个内存账户。
- `handler/account.go:100`：`BuyCrypto` 注释 “simulates buying cryptocurrency”，同样返回成功。
- `handler/contract.go:53-61`：`ContractLeverageSet` 只做参数校验，然后 `{"success": true}`，**没有调用任何交易所接口**。
- `TradingContractClassic.tsx:209` 把划转接口接到了真实 UI。

影响：用户点“划转 1000 USDT”，界面成功、内存余额变了、交易所一分钱没动；刷新后余额又回到真实值。这是最容易被用户当成“吞钱/资金不见了”的缺陷，也会污染对账。

补法（必须二选一）：

1. **接真**：按交易所实现 `Transfer`（Binance universal transfer、OKX transfer、Bybit transfer），成功以交易所返回为准，失败原样透传。
2. **明确不支持**：不做真实划转的交易所返回 `501 Not Implemented`，前端置灰并标注“该所暂不支持应用内划转”。

同时把 `/account/buy` 下线或改成“跳转交易所法币入口”，不要返回假成功。

验收：划转后交易所余额变化 = 应用内余额变化；对账差异为 0；不支持的所不会出现成功提示。

---

### G-02 杠杆 / 保证金模式 / 双向持仓没有落地（P0）

现状：

- CRA 参数里有 `leverage`、`margin_mode`、`position_side`，但 `adapter/binance.go` 的 `PlaceFuturesOrder` **完全不使用 leverage**，也没有单独的 `POST /fapi/v1/leverage`。
- 没有任何地方调用 `marginType`（逐仓/全仓）或 `dualSidePosition`（双向持仓）。
- `GET /contract/margin` 全部返回 `null`（注释：无账户级数据源）。

影响：

- 用户在策略里设 10x，实际按账户当前杠杆执行，仓位与风险敞口不是用户以为的那一套。
- 双向策略（`direction=dual`）在单向持仓账户上会被交易所拒绝或变成减仓。
- 保证金率、可用保证金、强平价无法展示，风控只能靠本地估算。

补法：账户绑定成功后做一次“合约账户初始化”：读 `positionRisk` / `leverage` / `marginType` / `dualSidePosition`，与策略要求比对；不一致则设置或拒绝启动；把结果缓存并展示。

验收：策略启动前能校验“杠杆=10x、逐仓、双向”，不一致给出明确错误；`/contract/margin` 返回真实值。

### G-03 交易所能力矩阵三处口径不一致（P1）

现状：

- `handler/config_dynamic.go:64-73`：只有 Binance/OKX/Bybit 是 `active`，Coinbase/Gate/MEXC/Bitget/KuCoin/HTX/Phemex/Deribit 全是 `stub`。
- 仓库里实际存在 `bitget.go`（14KB）、`gateio.go`（12KB）、`mexc.go` 等适配器。
- README/清单又说“Binance 深度 + 9 家基础 REST”。

影响：用户/运营不知道哪家真的能交易；新所接入没有验收标准；出问题无法判断是“没接”还是“接坏了”。

补法：建立唯一的 `exchange_capabilities` 注册表（代码常量或 DB），字段：`spot/futures/margin/transfer/ws/order_types/leverage/margin_mode` + `certified: bool` + `last_certified_at`。UI、路由、启动校验全部读它。

验收：任一交易所的能力只在一个文件里改；前端展示与后端行为一致。

---

### G-04 下单没有幂等键（P0）

现状：全仓库没有 `clientOrderId` / `newClientOrderId` 的生成与透传（只有社交提现用了幂等）。交易所都支持客户端订单号，但代码没用。

影响：

- 网络超时、重试、策略重启、批量启动都可能重复下单。
- 无法用交易所订单号反查本地订单，只能靠 symbol+时间猜。

补法：每笔订单生成 `xt-{botID}-{seq}-{hash}` 作为 `clientOrderId`，落库唯一索引；下单前先按 clientOrderId 查交易所；超时后用 clientOrderId 对账而不是盲目重试。

验收：模拟 100 次超时重试，交易所侧只产生 1 笔订单；本地订单与交易所订单 1:1 可追溯。

---

### G-05 无限频预算、无 429 退避、无时钟校验（P1）

现状：`adapter` 里只有 IBKR 对 429 做了 3 次指数退避；Binance/OKX/Bybit 没有 weight 预算、没有 `X-MBX-USED-WEIGHT` 读取、没有 NTP 偏移检查；`recvWindow` 固定 5000ms。

影响：多策略 + 多 symbol 轮询时容易触发 IP 级封禁；本机时钟漂移会导致签名 `timestamp` 被拒。

补法：按交易所维护 weight bucket（读取响应头，剩余权重低于阈值时排队）；429 统一指数退避 + 抖动；启动时做一次服务器时间偏移校准，超过 1s 告警。

验收：100 个并发请求下不出现 418/429；时钟偏移 2s 时自动校正并记录。

---

### G-06 行情数据面分裂（P0）

现状：`exchange/binance_ws.go` 推 tick / 盘口，`market/kline_feeder.go` 另走 REST 每 20 秒拉 K 线；两者时间基准、重连策略、去重逻辑都不同。

影响：策略看到的价格与盘口不同步；K 线收盘延迟；WS 断线后策略无感知。

补法：统一 `MarketDataPlane`：WS 为主，REST 只做启动回填与断线补偿；收盘 K 线由 WS kline 流生成；所有消费者（策略、Paper、TP-SL、前端）订阅同一总线。

验收：WS 断开 3 秒内自动重连并补齐缺失 K 线；策略不收到重复 bar。

---

### G-07 账户无复式账本（P1）

现状：余额在 `portfolio.Manager` 的 `map[string]*model.Balance` 内存里；DB 只有 `xt_portfolio_snapshots` 快照与 trades/positions，没有余额流水表；没有借贷/手续费/资金费/已实现盈亏的复式记账。

影响：无法解释“为什么余额从 A 变成 B”；对账只能比快照；分润、返佣、点卡扣费都没有可靠的记账基础。

补法：引入 append-only `ledger_entries`（账户、币种、方向、金额、余额快照、业务单据号、幂等键），所有余额变动必须过账；快照只做校验。

验收：任一时点余额可由流水重算复现；对账差异能定位到具体流水。

---

### G-08 单进程单库，无 worker 隔离（P1）

现状：API、策略循环、回测、超参、ML、WS、撮合全在一个 Go 进程；SQLite 单写者；没有任务租约/心跳。

影响：一个重回测会拖慢下单；一个策略 panic 可能带崩全部；多实例部署会争抢 SQLite 写锁。

补法（按阶段）：

1. 先把回测/超参/ML 移到独立 worker（同库只读，结果回写）。
2. 策略运行时加租约（strategy_id + owner + heartbeat），支持多实例主备。
3. 规模再上一个台阶时再评估 PostgreSQL + 队列（现在不必）。

验收：回测 100% CPU 时，下单 API P99 不受影响；worker 崩溃后任务可被其他实例接手。

---

### G-09 风控是“单笔检查”，缺组合级（P1）

现状：`risk` 有 13 项检查 + 限频，覆盖单笔名义、仓位、杠杆、保证金率等；但没有组合级：账户总保证金率、相关性/集中度、策略级最大回撤熔断、日内亏损停牌。

影响：CRA 多机器人并行时，单笔都合规、组合可能已经爆仓；极端行情没有“全局刹车”。

补法：增加 `PortfolioRisk`：按用户/账户聚合保证金率、净敞口、同向集中度；触发阈值时全局暂停新开仓（只允许减仓）；策略级日亏上限自动停。

验收：模拟三机器人同向满仓，组合保证金率超阈值时 1 秒内拒绝新开仓并告警。

---

### G-10 CRA 商业化闭环缺失（P1/P2）

已缺的具体项：

| 功能 | 现状 |
|---|---|
| 点卡 / 按机器人计费 | 无。`credits` 只有充值/推荐返佣，没有按运行时长/机器人扣点 |
| 激活码 | 无（全仓库无 activation/redeem） |
| 我的社区 / 团队 / 等级极差佣金 | 只有单层推荐码（`referral_repo.go`），无多级团队 |
| 用户收益榜（日/月/总） | 只有策略排行榜（`StrategyLeaderboard`），无用户收益维度 |
| 点卡不足 / 燃料预警 | 无余额阈值告警（只有风险/指标告警） |
| 策略学堂 / 新手指南 / FAQ / 客服 | 无对应页面 |
| 盈利保护全所 | 只有 Binance `TransferFromFuturesToFunding`；OKX/Bybit/Bitget 无划转 |

补法：先做“点卡计量 + 低余额提醒 + 收益榜”三件（直接影响收入与留存）；激活码与多级团队其次；帮助中心最后。

验收：机器人启动即扣点、停止即结算；余额低于 3 天用量时站内信 + 邮件；收益榜可按日/月/总切换。

---

### G-11 交易审计缺失（P2）

现状：`audit_repo` 只服务 agent token；改参数、手工平仓、批量删除、划转没有统一审计流水。

补法：所有写操作记 `who / what / before / after / source_ip / request_id`，保留 180 天。

## 六、TypeScript 前端缺口

### F-01 移动端只是 WebView 壳（P1）

现状：有 `capacitor.config.ts`，但本质是加载打包后的 Web；无推送、无生物识别、无离线缓存、无移动专用布局。

CRA / CryptoRobotics 都是移动优先。影响获客与留存。

补法：先做移动端专用底部导航 + 单手操作布局 + 推送（订单/成交/风控），再做生物识别解锁。

---

### F-02 运营与帮助页面缺失（P1）

缺：策略学堂、新手指南、FAQ、在线客服、版本更新说明、点卡钱包、团队/佣金页、用户收益榜。

现有 `Billing.tsx` 只覆盖充值与推荐，不足以支撑 CRA 式增长闭环。

---

### F-03 批量操作入口分散（P2）

现状：后端已有 `batch-start/stop/close/delete`，前端只在 `StrategyList` + `StrategyBatchEditModal`；`BotsCenter` 里没有批量操作台。

CRA 的“一键启动/一键平仓/一键设置/删除/执行历史”是一个独立工作台。

补法：在机器人中心加“批量操作”抽屉，复用现有 API；补“批量改参数/批量改杠杆”。

---

### F-04 前后端契约漂移（P2）

现状：`web/src/lib/api.ts` 手写 589 条路由的类型；后端没有 OpenAPI 导出；空实现端点（transfer/leverage）前端无法感知。

补法：后端生成 OpenAPI，前端用 openapi-typescript 生成类型；对 `simulated/unsupported` 打标记，前端自动置灰。

---

### F-05 图表内下单/高级订单交互（P2）

现状：有合约图表与 `AdvancedOrderManagement`，但没有 CryptoRobotics 那种“图上拖拽止盈/止损、OCO 三腿可视化”。

补法：图表叠加持仓线、强平线、TP/SL 可拖拽；拖拽后回写策略参数。

---

### F-06 面板 5 秒轮询而非 WS（P2）

现状：`BotsCenter` 运行面板注释写明 5s 轮询；后端其实有 WS hub。

补法：订单/成交/持仓/风控事件走 WS，前端只保留兜底轮询。

## 九、现在不建议做的

1. **不要为了“三栈”把策略引擎重写成 Rust。** freqtrade 的 Python 单进程能跑，Go 的策略运行时不是瓶颈；先把撮合/持仓/TP-SL 收口。
2. **不要在 100 个并发机器人之前上 Kafka/PostgreSQL 集群。** 先把单进程内的任务隔离、租约、账本做对。
3. **不要同时补 8 家交易所。** 先把 Binance/OKX/Bybit 做到“下单-撤单-查仓-划转-WS-对账”全绿，再复制。
4. **不要继续加策略数量。** 20 个内置策略已经足够；现在缺的是每个策略的“可解释成交”。
5. **不要保留死代码。** Rust executor 要么接线，要么删除；两套 TP/SL 是最典型的长期负债。
